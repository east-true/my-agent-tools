# 파일시스템 연속 작업

기본 조건은 명령을 독립적으로 한 번 사용하는 것이다. 파일 한 곳의 단순 검색·치환은 직접 명령으로 작업과 검증을 끝낼 수 있다면 그 방법도 선택한다. 아래 조합은 이미 지시된 작업에 필요한 단계만 함께 실행한다. `fs apply`의 계획 생성·검증·반영·재검증은 모델 입력 캐시 없이 수행하며 연속 실행을 요구하지 않는다.

요청과 검증된 결과만으로 다음 동작이 결정되는 연속 작업은 로컬 스크립트에서 함께 실행합니다. 중간 단계마다 모델 호출을 추가할 필요가 없습니다. 직접 처리도 같은 방식으로 배치할 수 있으며 작성·후처리·실패 복구·최종 검증 비용까지 비교합니다.

증분 비교는 기준 생성 → 이미 지시된 파일 작업 → `--peek --comparisons 2`를 순서대로 실행할 수 있습니다. 각 단계의 성공·완전성을 확인한 뒤 다음 단계로 진행하고, 실제로 필요한 최종 변경 구간과 기준 보존·반복 일치 근거를 반환합니다. 두 번의 실제 스캔은 그대로 수행합니다. 사람의 판단이나 다른 작업 사이의 관찰이 필요하면 개별 명령을 사용합니다.

변경 확인이 한 번만 필요하면 `--comparisons 2`를 추가하지 않습니다. 기존 기준으로 다른 작업 후 복귀해 조회할 수 있지만 같은 루트·선택 범위의 기준인지 확인합니다. 최초 기준 생성은 변경 전 기록을 저장하는 단계이므로 독립 1회 변경 조회의 절감으로 계산하지 않습니다. 기준이 없으면 현재 파일 확인에는 `inspect`를 사용합니다.

수정 조건이 이미 승인되었다면 `--spec --save-plan --apply --report-changes`로 계획 생성·저장·전체 검증·반영·재검증을 처리합니다. `complete`, `report_complete`, 파일별 `verified`, `saved_plan.verified`가 모두 참인지 확인합니다. `saved_plan`의 형식·파일 수·SHA는 실제 저장 파일의 재검증 근거이므로 같은 증명을 위해 계획을 다시 출력할 필요가 없습니다. 계획 원문이 후속 작업에 필요할 때는 저장 파일을 읽습니다.

동일한 치환은 spec의 `groups`에서 경로 목록과 치환 조건을 한 번만 작성합니다. 각 파일의 횟수·SHA를 따로 검증하고 저장 계획은 기존 개별 파일 형식으로 펼칩니다. 실패하면 여러 독립 파일의 `diagnostics`를 한꺼번에 읽어 수정할 항목을 파악합니다. 같은 파일의 앞선 치환이 실패한 뒤 조건은 추측하지 않으며 승인 없이 횟수를 바꾸지 않습니다.

오류 복구까지 지시되었다면 구조화된 `diagnostic`의 경로·치환 번호·기대·실제 횟수를 승인된 복구 범위와 대조합니다. 그 범위에 맞는 항목만 복사본에서 고친 뒤 전체 조건을 다시 검증합니다. 예기치 않은 오류와 승인 범위 밖의 차이는 중단하고 보고합니다. 횟수를 자동 완화하거나 검증을 생략하지 않습니다.

횟수 수정 대상이 입력 배열의 위치로 이미 명확하게 지시되었다면 `--spec --recount FILE_INDEX:REPLACEMENT_INDEX --save-plan --apply --report-changes`로 그 복구까지 이어집니다. 원래 진단은 `corrections`에 남고 해당 항목만 재계수합니다. 이 요청에서는 별도의 실패 호출·Python 수정 코드·입력 JSON 재출력이 필요 없습니다. 일반적인 횟수 오류에는 이 옵션을 임의로 추가하지 않습니다.

조회한 조각으로 편집할 때는 `inspect --raw --hash`의 정확한 `text`와 원본 SHA를 계획에 사용합니다. 기본 출력 상한에서 시작하고 `next_cursor`가 있을 때만 이어 읽습니다. 상한을 줄여 추가 호출을 만드는 방식으로 절감을 판단하지 않습니다.

문서 제목을 알고 있으면 `inspect --section TITLE --raw --hash`로 하위 섹션을 포함한 원문을 바로 조회합니다. 여러 파일의 서로 다른 제목·중복 제목의 순번은 기존 `--request`에 `sections`로 지정합니다. 구조 목록이 요청됐을 때만 `--outline`을 추가하며 목차를 실제 본문 검토의 대체물로 사용하지 않습니다.

테스트 프로세스가 종료된 뒤 `test-results`로 보고서 집계까지 이어 확인합니다. `complete`는 보고서 판독의 완전성이므로 실제 종료 코드·실패·오류·skip·보고서 소속을 함께 확인합니다. 기존 파일은 이번 실행의 증명이 아니며 `execution_verified`는 false입니다. 작은 XML 한 개의 단순 조회에는 직접 처리도 허용합니다.

값을 읽은 뒤의 수정 규칙까지 승인된 정수 증감은 [연결 실행 예제](../../examples/fs/edit-integer.py)를 재사용할 수 있습니다. Python 3와 tools가 PATH에 있을 때 다음 한 번의 로컬 실행으로 조회·SHA 검사·계획 생성·적용·원문과 권한 read-back까지 수행합니다.

```sh
python3 examples/fs/edit-integer.py --root . --path settings.py --key retry_budget --amount 3 --expect timeout=30
```

`--expect`는 그대로 유지할 정수 값의 사전 조건이며 반복 가능합니다. 불일치·중복 할당이면 쓰기 전에 종료합니다. 결과의 value와 preserved_integers는 실제 읽은 값이고 before/after SHA·verified·unrelated_preserved는 Go apply의 최종 원문·권한 검증을 통과한 근거입니다. 조건이 이미 결정된 작업에서는 중간 JSON 전체를 출력하거나 같은 완료 상태를 다시 읽지 않습니다. 내부 CLI는 inspect와 apply 두 번이며 모델 중간 판단이나 입력 캐시를 요구하지 않습니다. 편집 해석에 판단이 필요한 작업은 조회 뒤 모델의 판단을 유지합니다. 예제 설치·발견 비용은 환경에 따라 별도로 발생합니다.
