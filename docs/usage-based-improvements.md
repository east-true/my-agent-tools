# 실제 사용 기록에 근거한 개선안

2026-10-11 사용 기록 분석과 구현 근거다. 분석 당시의 문제와 제안은 아래에 보관하며, 구현한 기능은 [`pr reviews --conversation --save-result`](github/pr/reviews.md), [`pr inspect --conversation`](github/pr/inspect.md), [`fs test-results`](fs/test-results.md), [`fs inspect --outline --section`](fs/inspect.md)이다. 실제 작업 전체의 AND 달성 여부는 구현 자체와 구분해 측정한다.

## 확인 범위와 해석

`/home/kft/work` 아래 저장소의 세션을 공용 Codex 세션 파일에서 `session_meta.cwd`로 찾고, 읽기 전용 세션 DB의 목록과 대조했다. 하위 작업 경로에 연결된 세션은 267개이며, 현재 경로가 존재하는 세션은 247개다. 그중 Git 저장소 17곳에 속한 세션은 246개이고 나머지 1개는 `test` 경로다. 상위 `work` 경로에서 시작한 6개 세션도 별도로 확인했다. 저장소 경로가 사라진 기록은 현재 저장소의 사용 횟수에 합산하지 않았다. 세션이 발견되지 않은 저장소의 사용을 추정하지 않았다.

현존 저장소 중 이 도구 자체의 개발 기록을 제외하면, 도구 입출력이 있는 15곳·200개 세션에서 41,193개 호출 응답을 색인했다. 이는 모델 도구 호출 기록 수이며 셸 명령·내부 CLI·API 호출 수가 아니다. 입력 패턴으로 후보를 찾고 대표 사례의 요청, 입력, 출력과 다음 호출을 확인했다. 모든 호출의 필요성을 개별 판정한 전수 감사나 토큰 절감률 측정은 아니다. 검색용 응답 사본은 앞부분 24,000자로 제한했으며 원본 세션은 수정하지 않았다.

세션 내용은 그대로 저장소에 복사하지 않는다. 아래에는 필요한 동작과 재현 단서만 남긴다. 호출 사이의 시각 차이는 모델 판단·다른 작업·승인 대기를 포함할 수 있으므로 명령 실행 시간으로 사용하지 않는다.

## 1. `github pr reviews`: 수집 재사용과 필요한 대화 범위

### 실제로 필요했던 입출력

- `romni-order-web-client`, 2026-10-08: PR의 코드 경고를 확인하면서 PR head, inline 댓글, 일반 대화 댓글(`/issues/{number}/comments`)을 각각 조회했다. 이후 Check Run annotation과 관련 소스를 읽었다.
- `romni-stay-server`, 2026-08-27: annotation, inline 댓글, 일반 대화 댓글을 함께 조회한 뒤 Java 원문과 테스트를 읽었다.
- `dockpilot`, 2026-08-23~24: 미해결 스레드의 경로·줄·본문을 읽고 실제 소스·테스트를 확인했다. 별도 PR 조회에서는 일반 댓글에 리뷰 실행 제한 안내가 있었다. 빈 스레드 목록만으로 리뷰가 수행됐다고 판단할 수 없었다.

분석 당시 `pr reviews`는 미해결 스레드와 제출된 리뷰 이력을 수집했지만 일반 대화 댓글은 포함하지 않았다. `pr inspect --sections reviews`도 같은 범위였다. 원문 보존·전체 페이지 수집은 이미 구현되어 있었으므로 다시 개선 항목으로 제시하지 않았다.

### 우선 개선: 같은 작업 안의 전체 수집 반복 제거

현재 [리뷰 반영 측정](benchmarks/github/pr/reviews.md)은 AND를 충족하지 못했다. [실행 기록](benchmarks/actionable/data/study.json)의 tools 세 실행은 셸 항목이 각각 2개였지만 `pr reviews` 자체를 각각 2·3·3회 실행했다. API 요청은 6·9·9회였고 직접 처리는 모두 3회였다. 두 실행에서는 처음 받은 자료가 있는데도 수정 스크립트 시작 시 다시 전체 리뷰를 수집했다.

먼저 최초 JSON을 같은 작업의 로컬 입력으로 보관하고, 수정 요청 해석·대상 확인에 재사용한다. 두 번째 전체 수집을 의무화하지 않는다. 이 저장·읽기 비용도 전체 작업 비교에 포함한다. 모델 입력 캐시 적중이나 명령 연속 반복을 전제로 하지 않는다.

최종 확인은 요청한 증명 범위에 맞춘다. 파일 수정 후 현재 head 확인만 요구했다면 새 head 조회와 실제 파일 재검증으로 끝낼 수 있다. 최신 리뷰 상태까지 확인해야 한다면 head만으로 대신하지 않는다. 동일 head에서도 새 댓글·본문 수정·해결 상태가 바뀔 수 있다. 현재의 `pr inspect` 상태 조회를 재사용하거나, 저장한 수집 결과를 입력으로 받는 재확인 기능을 공통 수집 로직 위에 검토한다. 수정 시각·ID로 변경을 확인할 수 없는 자료는 다시 수집한다.

이 반복이 평균 시간 증가 전체의 원인이라고 단정하지 않는다. API 응답·본문 처리·스크립트 작성 부담을 줄일 근거는 있지만, 새로운 작업 전체 측정 전에는 AND 달성이라고 표시하지 않는다.

### 기능 개선: 일반 대화 댓글을 선택적으로 함께 수집

`--conversation` 같은 명시적 선택으로 일반 대화 댓글까지 같은 결과에 담는다. 댓글 ID·작성자·전체 본문·URL·수정 시각과 페이지 완전성을 유지하고 inline 스레드, 제출 리뷰, 일반 댓글을 구분한다. 기존 기본 범위를 확대하지 않는다.

입력은 PR 번호와 필요한 수집 범위이며, 출력은 그 범위의 정확한 현재 자료다. 위 실제 사례에서 별도 일반 댓글 조회를 줄일 수 있다. 코드 경고의 annotation은 여전히 별도 근거이므로 대화 댓글로 대체하지 않는다. 리뷰 이력을 제외하는 선택도 실제 요청이 미해결 대화만 요구할 때 검토하며, 제출 리뷰에 있는 수정 요청을 임의로 버리지 않는다.

새 옵션을 늘리기 전에 기존 `pr inspect` 선택 범위와 공통 수집기에 반영할 수 있는지 확인한다. 재확인·캐시 기능을 별도 구현으로 복제하지 않는다.

## 2. 파일시스템: JUnit 결과 읽기

### 실제로 필요했던 입출력

`romni-stay-server`, 2026-10-03의 같은 작업에서 `TEST-*.xml`을 순회하고 `tests`, `failures`, `errors`, `skipped`를 합산하는 Python 코드를 반복 작성했다. 처음에는 66개, 이후에는 67개 테스트가 반환됐다. 당시 테스트 프로세스가 진행 중이어서 먼저 읽은 보고서가 최종 결과를 보장하지 않았다.

`romni-payments-server`, 2026-10-03에는 `test`·`acceptanceTest`별 XML을 합산하고 “reports available so far”로 표시했다. 기록 전체의 관련 Python/XML 입력 패턴 후보는 208건이었다. 이 수는 고유 작업 수·불필요한 재조회 수가 아니며, 정상적인 새 실행 후 확인도 포함한다.

### 개선안

`fs test-results` 같은 읽기 전용 JUnit 집계 기능을 검토한다. 입력은 실제 보고서 경로·glob·명시한 suite 범위다. 출력은 suite별 전체 수·실패·오류·skip, 발견한 보고서 수, 실패 testcase와 원문 진단, 파일 근거·읽기 오류·완전성이다. 중첩 suite의 합계를 중복 계산하지 않는다.

핵심은 테스트 실행 종료를 확인한 뒤 결과 집계까지 이어 쓰게 하는 것이다. 보고서가 없거나 XML이 잘못됐을 때 0개 성공으로 표시하지 않는다. 기존 보고서만 읽었다면 이번 실행의 성공이라고 주장하지 않으며, 실행 중 보고서와 재사용된 보고서를 구분할 근거가 없으면 그 한계를 반환한다. 보고서 판독만으로 프로세스 종료를 증명할 수는 없다. 기존 파일을 자동 삭제하거나 테스트를 임의로 재실행하지 않는다.

여러 suite 집계와 실패 진단에 필요한 Python 작성·로그 재검색을 줄일 수 있다. XML 하나의 필드 몇 개만 읽는 작업까지 이 명령을 강제하지 않는다. 보고서 파서 작성 비용까지 포함한 완료 작업 비교에서 이점이 있는 경우에만 개선으로 채택한다.

## 3. `fs inspect`: Markdown 구조와 섹션 조회

### 실제로 필요했던 입출력

`tmp/romni-stay-server`, 2026-10-03: 멀티 프로젝트별 README·docs를 분리하는 요청에서 문서 목록과 본문을 여러 파일에 걸쳐 출력했다. 응답이 잘린 뒤 README 범위를 바꿔 읽었고, 문서별 제목 목록을 얻으려고 Python 순회 코드를 작성했다. 작업 중에는 파일 경로·문서 제목·섹션 위치와 실제 해당 본문이 필요했다.

고정 줄 수의 문맥, 파일별 범위, 겹친 구간 병합은 이미 `fs inspect`에 있다. 이것을 새 기능으로 다시 제안하지 않는다.

### 개선안

기존 inspect의 요청 형식에 Markdown 목차와 명시한 제목의 전체 섹션 조회를 추가하는 방향을 검토한다. 목차는 경로·제목·수준·시작/끝 줄을 반환하고, 섹션 요청은 필요한 하위 섹션을 포함한 정확한 원문·줄 번호·선택적 SHA를 반환한다. 여러 파일은 기존 요청 배치와 출력 상한·커서 계약을 사용한다.

코드 블록 속 `#`를 제목으로 해석하지 않고, 중복 제목은 위치나 순번으로 선택하게 한다. 제목을 알고 있는 작업은 목차 선행 조회 없이 섹션을 직접 요청한다. 구조를 알아야 선택할 수 있는 작업은 목차와 본문 선택이 두 단계일 수 있으며 그 비용도 계산한다.

전체 문서 내용을 재배치하거나 의미를 검토하는 작업은 결국 전체 원문이 필요할 수 있다. 그런 작업에서 목차가 원문 조회를 대체한다고 주장하지 않는다. 실제 구조 파악·알고 있는 섹션 조회에서 임시 Python 작성과 중복 본문 출력을 줄이는 범위만 후보로 삼는다.

## 추가 변경 근거가 약한 항목

| 항목 | 현재 판단 |
|---|---|
| `issue create`, `issue branch`, `pr create` | 과거 측정의 캐시 포함·제외 지표가 상충한다. 실제 기록의 이슈→연결 브랜치→워크트리와 푸시→PR 단계는 이미 조합 명령에서 제공한다. 캐시 차이만을 근거로 검증이나 응답 필드를 더 줄이지 않는다. |
| `dependabot view` | 과거 측정에서 양쪽 모두 API 한 번이었다. 필요한 단일 필드의 직접 조회를 허용하고, 실제 후처리 부담이 확인되지 않은 새 옵션은 추가하지 않는다. |
| `fs apply` 패치 재시도 | 실제 기록에 원문과 다른 행 배치·문장 형태를 가정해 `apply_patch`가 실패한 사례가 있다. 이는 현재 `fs apply` 실행의 실패 증거가 아니다. 정확한 원문 조회와 기존 전체 검증을 활용하며, 유사 문장 자동 적용·횟수 자동 완화는 제안하지 않는다. |
| `fs delta` 반복 확인 | 수정 후·테스트 후 새 상태 확인은 필요할 수 있다. 기존 반복 관찰 기능을 기본값으로 켜거나 서로 다른 시점의 확인을 하나로 합치지 않는다. |
| 일반 검색·짧은 치환 | 자연스러운 `rg`·직접 치환이 한 번에 끝나는 작업은 유지한다. 새 JSON 형식·스냅샷·미리보기 작성 부담을 추가하지 않는다. |

## 채택 전 검증

먼저 위 대표 작업의 입력·요구 결과·최종 상태·검증 범위를 고정하고 모델 없는 재현으로 누락, 실제 호출, 후처리 필요성을 확인한다. 그다음 변경한 작업만 기본 모델·추론 강도로 비교한다. 직접 처리에도 같은 배치·필터를 허용하고 입력 작성, 필요한 최초 조회, 저장, 수정, 오류 복구와 최종 확인까지 집계한다.

검증되지 않은 새 기능은 모두 개선 후보다. 독립 1회 사용에서 캐시 포함 총 입력+출력과 작업 효율이 함께 좋아지고, 캐시 제외 지표·실패·추가 호출을 숨기지 않아야 AND 달성으로 판정한다. 기존 부분 개선의 유지와 새 기능의 채택 판단은 구분한다.

구현 시 Go의 경로·프로세스·파일 API로 OS 독립성을 유지하며, Linux 실행 확인과 macOS·Windows 빌드/실제 동작 확인을 구분한다.

## 구현과 완료 검증 결과

최초 구현의 기본 설정 비교 42회는 모두 요청한 정답·파일 상태를 충족했다. 하지만 직접 처리와 비교해 **안정적인 AND 달성이 확인된 항목은 없다**. [명령별 최신 수치·전체 불리한 기록](benchmarks/usage/README.md)을 함께 확인한다.

- JUnit 일반 판독은 셸 실행 3→1과 평균 시간·총 토큰이 줄었지만 캐시 제외 토큰이 늘어 조건부다. XML 오류 처리는 별도 표본으로 보존한다.
- 일반 대화 조회는 head 확인 근거를 출력해 불필요한 PR 재조회가 줄었다. 직접 GraphQL 배치보다 API 수가 많고 캐시 제외 지표가 상충하며 시간 편차도 커 일반적인 AND라고 판정하지 않는다.
- Markdown 조회는 평균 시간이 줄었으나 총 토큰이 증가했다. 문서 구조·정확한 섹션의 조회 기능은 유지하고 단순 조회에 의무화하지 않는다.
- 리뷰 반영은 필요한 원문·보관·검증을 제공해도 사용 과정의 도움말/파일 재조회가 늘었다. 알려진 작은 파일은 직접 읽기·수정·검증을 배치하는 방법도 계속 허용한다.
- 명시한 raw 파일 요청은 원문 없이 메타데이터만 주던 동작을 고쳤다. 같은 바이트·SHA를 얻는 [모델 없는 전후 확인](benchmarks/usage/data/raw-file-native-comparison.json)은 CLI 2→1이지만, 별도의 작업 전체 6회 비교에서는 직접 처리 대비 시간·총 토큰이 줄지 않았다. 두 결과를 섞어 절감이라고 표현하지 않는다.

측정 도중 확인한 불리한 결과를 삭제하거나 좋은 실행으로 교체하지 않았다. 최신 코드의 주석·블록 표현은 새 작성 규칙에 맞춰 정리했으며, 각 측정에 고정한 원래 소스와 실행기는 SHA와 함께 그대로 보존한다.


## 후속 개선과 최신 완료 비교

리뷰·대상 파일의 원문/SHA 묶음, 스레드·제출 리뷰의 첫 페이지 배치, 공통 Markdown 순번, PR 생성 결과의 최종 브랜치 검증과 연결 수정 예제를 개선했다. 변경한 작업만 기본 설정으로 36회 비교했고 모두 정답·파일 상태를 통과했다. 각 명령의 최신 문서와 원본을 우선한다.

- PR 생성은 총 토큰 −59.0%, 캐시 제외 −15.0%, 시간 −60.6%이며 API 수가 같고 셸 실행 수가 줄었다. 생성 결과로 실제 브랜치를 확인할 수 있다.
- Markdown 조회는 총 −42.0%, 캐시 제외 −23.3%, 시간 −50.2%, 셸 2→1로 표본에서 AND를 충족했다.
- 연결 수정 예제는 보존 조건의 실제 값까지 검증·반환한 후 총 −2.3%, 캐시 제외 −5.2%, 시간 −47.9%, 셸 1→1로 표본에서 AND를 충족했다. 내부 inspect·apply 두 CLI 비용을 포함하며 예제 설치·발견 비용은 제외한 조건이다. 앞선 연결 수정의 총 +56.4% 실행도 보존했다.
- 리뷰 반영은 셸 3.33→2회지만 총 +0.6%, 캐시 제외 +31.6%, 시간 +6.4%로 AND를 충족하지 못했다. 캐시 제외 편차·추가 head 검증·직접 배치의 차이를 보존하고 자동 의미 해석·수정으로 억지로 줄이지 않는다.
- 일반 대화 조회는 총 −0.7%, 캐시 제외 −1.2%, 시간 −13.1%지만 API 직접 1→tools 3회로 조건부다. 이전 tools 4회 대비 요청 하나가 줄어든 구현이며 과거 토큰 수치와의 차이를 코드 효과로 계산하지 않는다.

[최신 사용 사례와 모든 코호트](benchmarks/usage/README.md) · [PR 생성](benchmarks/github/pr/create.md). 입력 캐시는 통제하지 못했고 소표본 평균의 조건 충족을 안정적인 실사용 효과로 확대하지 않는다. 부분 GraphQL 오류의 원문 유지 보완은 회귀 테스트로 확인했으며 해당 오류 경로의 모델 토큰은 별도 측정하지 않았다.
