# 전체 명령의 작업 효율·토큰 개선안

2026-10-11 기준 GitHub 15개와 파일시스템 4개, 총 19개를 점검했다. 목표는 **에이전트가 직접 처리하는 경우와 tools를 이용하는 경우를 같은 완료 작업으로 비교해 작업 효율 AND 전체 토큰 절감을 달성하는 것**이다. 다음 작업에 필요한 원문·위치·실제 상태·검증 근거를 한 번에 사용할 수 있게 제공하는 개선을 우선한다.

A1·A2·A4·A5와 A3의 단일 관찰 복구, A6의 공통 읽기 전용 조회를 구현했다. [구현·측정 결과](benchmarks/completion/README.md)를 함께 확인한다. 명령의 도움말·문서·구현과 기존 실행 기록을 확인했고, 출력 문제 세 가지를 모델 호출 없이 재현했다. 19개 도움말의 인증 없는 실행도 확인했다. 이는 19개 전체 작업의 새 기능 검증이나 토큰 재측정이 아니다. [관찰 결과·소스 SHA](benchmarks/command-usability-audit.json) · [재현 실행기](../scripts/benchmarks/audit_command_usability.py).

## 구현 결과

A1의 편집용 원문 축약과 A2의 제출 리뷰 누락을 고쳤다. A4는 저장 후 바이트·JSON·권한·SHA를 실제로 검증한다. A5의 공통 옵션은 `--review-sources`이며 명시한 미해결 스레드 경로만 읽는다. A6은 다섯 기존 명령의 `--read-evidence` 분기로 구현했고 원격 작업을 실행하지 않는다.

A3은 단일 관찰의 원문 보관·읽기 전용 복구를 구현한 뒤 실제 비교에서 추가 호출 부담을 확인했다. 필요한 구간을 미리 지정한 작업은 `--diagnostic-pattern`/`--report-pattern`과 문맥 옵션으로 최초 응답에서 원문·위치·완료 검증 근거를 받도록 다시 개선했다. apply는 내부에서 이미 확인한 권한 보존 결과도 제공한다. 전체 출력과 개별 복구는 유지하며 다중 comparisons의 보고서 복구는 지원하지 않는다.

새 측정은 직접 처리와 같은 완료 기준이다. 원문 복구 코호트와 세 선택 응답의 후속 코호트를 합산해 개선 효과라고 해석하지 않는다. 불리한 원문 복구·리뷰 결과도 보존한다. [명령별 최신 결과](benchmarks/completion/README.md)에서 캐시 포함·제외 토큰, 시간, 셸/CLI/API, 편차와 조건부 판단을 확인한다.

아래 내용은 구현 전 결함의 근거와 승인 기준이다.

## A1. 편집용 원문을 그대로 제공

구현 전 [`compactProjection`](../internal/cli/compact.go)은 이름이 text인 긴 문자열을 공통으로 잘라낸다. 새 source_files의 ranges[].text에도 적용된다. 실제 CLI에서 원문 2,700바이트를 함께 조회하고 compact를 적용하자 반환 원문은 1,200바이트가 됐으며 source_files.complete는 true이고 전체 자료는 별도 evidence_file에 보관됐다. 원문 전체가 필요한 작업은 그 파일을 다시 읽어야 한다.

편집용 소스의 text·lines를 구조상의 역할로 구분해 원래 바이트와 범위를 유지한다. CRLF·마지막 개행·SHA·선택 구간은 보존하고 중복 메타데이터만 줄인다. collection의 완전성과 반환한 원문 범위의 완전성을 혼동하지 않는다. 축약 표시를 추가하는 것만으로 재조회 부담이 없어졌다고 판단하지 않는다.

이 변경은 한 응답의 출력 토큰을 늘릴 수 있다. 승인 기준은 원문 재조회·artifact 해석·추가 입력 작성까지 포함한 완료 작업이 더 효율적이고 전체 토큰도 줄어드는지다. 직접 처리에도 리뷰·파일 읽기의 자연스러운 배치를 허용한다. 긴 소스의 끝부분에서 실제 수정 대상을 찾아 편집하고 SHA·다른 바이트·권한까지 확인하는 작업으로 비교한다.

## A2. unchanged에서도 제출 리뷰를 읽고 작업할 수 있게 제공

구현 전 [`inspectionItems`](../internal/cli/pr_state.go)는 제출 리뷰를 상태 파일에 보관한다. 하지만 outstandingInspection에는 제출 리뷰 배열이 없어서 변화가 없는 응답에는 그 본문이 나오지 않는다. inline 스레드 없이 제출 리뷰 본문에만 요청이 있는 상태를 재현하자 status는 unchanged, attention_required는 true였지만 요청 본문은 없었다.

reviews 범위를 선택한 복귀 조회에서는 현재 수집한 제출 리뷰의 원문·ID·작성자·상태·대상 커밋·시각·URL도 사용할 수 있게 제공한다. 이미 수집한 결과를 반환하므로 별도 원격 조회는 추가하지 않는다. 오래된 CHANGES_REQUESTED나 APPROVED의 본문을 자동으로 현재 수정 의무로 해석하지 않는다. 기록을 더 읽기 위해 --full을 다시 실행해야 하는 흐름을 줄이는 것이 목적이다.

범위가 checks뿐인 조회에는 리뷰 이력을 붙이지 않는다. 중복 본문은 같은 응답 안에서 제거할 수 있지만 최초 이력이나 이전 모델 문맥을 기억한다고 가정하지 않는다. 다른 작업 후 복귀, 제출 리뷰에만 요청이 있는 경우, 승인 본문의 코멘트, 변경·철회된 과거 이력을 포함해 원래 요청과 근거를 구분할 수 있는지 확인한다.

## A3. 큰 결과를 복구할 때 완료한 작업을 반복하지 않기

기본 상한에서도 큰 결과는 발생한다. JUnit의 긴 실패 진단을 기본 64 KiB 조건으로 조회하자 테스트 합계는 유지됐지만 진단이 생략됐고 complete=false, diagnostics_unavailable=true, 커서 없음으로 반환됐다. 매우 작은 상한을 강제한 시험이 아니다. [`fs delta`](../internal/filesystem/delta.go)는 출력 상한 초과 시 changes 전체를 비우며 기준을 갱신하지 않는다. [`fs apply`](../internal/filesystem/apply.go)는 쓰기·검증 상태를 유지하지만 큰 변경 구간을 생략하고 report_complete=false로 반환한다.

세 명령의 상태 변경 의미를 구분해서 개선한다.

- test-results: 완료한 합계·보고서 SHA를 유지하고 생략된 진단의 위치·수를 제공한다. 필요하면 같은 자료의 나머지 진단만 이어 읽는다. 파일이 바뀌면 이전 합계와 새로운 진단을 섞지 않는다. 실행 완료는 여전히 보고서 판독으로 증명하지 않는다.
- delta: 가능한 변경 경로·종류·SHA와 아직 전달하지 못한 구간을 남긴다. 원래 선택 범위와 관찰한 내용에 연결된 이어 읽기를 검토한다. 전달이 불완전하거나 파일이 바뀌면 기준을 자동 전진하지 않는다. 사후 파일 조회로 삭제된 원문을 복원할 수 있다고 가정하지 않는다.
- apply: 요청한 큰 변경 보고서를 원문·SHA와 함께 보관하는 선택 기능과 읽기 전용 보고서 조회를 검토한다. 원래 계획을 다시 적용해 보고서를 얻는 흐름을 만들지 않는다. 적용 여부·파일별 검증·부분 실패는 처음부터 유지한다. 저장된 작업 보고서와 이후의 현재 디스크 상태는 구분한다.

단순히 출력 상한을 작게 만들거나 모든 결과를 파일 참조로 바꾸지 않는다. 일반적인 작은 작업은 기존 한 응답으로 완료한다. 원문 보관·조회·페이지 조립·SHA 재확인·파일 I/O 비용을 포함해서 현재의 재조회 방식 및 자연스럽게 필요한 부분만 읽는 직접 처리와 비교한다. 커서가 늘어나 전체 호출이 더 많아지면 그 상충을 기록한다.

## A4. 설정 저장의 실제 검증 근거 제공

구현 전 [`setup`](../internal/cli/setup.go)은 원래 파일의 변경을 검사하고 저장하지만, 성공 결과는 계획과 path·status만 반환한다. 저장 완료 후의 파일 read-back·SHA 근거는 없다. 사용자가 실제 저장 파일의 내용과 상태까지 확인해 달라고 요청하면 에이전트가 추가 조회를 작성해야 한다.

저장된 바이트·JSON·기존 권한을 실제로 확인하고 saved_config에 SHA·verified·변경 여부를 제공한다. 계획과 실제 저장 상태를 구분하며 dry-run은 saved 검증을 주장하지 않는다. 검증 실패 시 대상 경로와 이미 저장된 사실을 유지하고 부분 실패로 보고한다. 확인 뒤 다른 프로세스가 변경하는 것까지 보장하지 않는다.

설정 저장과 실제 적용 내용 확인까지 같은 작업으로 비교한다. 직접 처리에도 저장과 read-back의 한 스크립트를 허용한다. 현재 setup이 이미 한 호출로 끝나는 단순 저장에서는 추가 검증 비용이 이득을 보장하지 않으므로 결과를 구분한다.

## A5. 조회 전에는 모르는 리뷰 파일 경로 처리

기존 --source-path는 조회 전에 경로를 알아야 한다. PR 번호만 알고 리뷰 수정을 시작하는 작업은 스레드를 받은 뒤 경로를 모아 fs inspect 입력을 만들고 다시 조회해야 할 수 있다. 이미 알려진 파일은 현행 --source-path로 충분하다.

명시적으로 선택한 경우에만, 수집한 미해결 스레드의 실제 파일 경로를 중복 제거해 기존 파일 조회로 연결하는 옵션을 검토한다. pr reviews와 reviews 범위를 선택한 pr inspect에서 같은 로직을 사용한다. 최종 옵션 이름은 구현 전 고정하고 읽기 계약을 공유한다. 제출 리뷰 본문에서 경로나 수정 의도를 추론하지 않으며 의미에 따른 자동 편집은 추가하지 않는다.

로컬 root·경로 검증·파일/바이트/출력 상한·SHA를 유지한다. 삭제된 파일·없는 파일·오래된 스레드 위치는 명확하게 보고하며 실제 현재 줄로 추측해 대체하지 않는다. 로컬 원문이 원격 head와 같다고 주장하지 않는다. 소스를 요청하지 않은 조회의 기본 범위는 늘리지 않는다.

경로를 알려주지 않은 리뷰 작업에서 수집·경로 매핑·파일 조회·실제 편집·최종 검증까지 비교한다. 직접 처리도 결과에서 경로를 읽어 파일을 조회하는 배치를 사용할 수 있다. 관련 없는 대형 파일까지 읽어 토큰이 증가하거나 기본 범위가 넓어지면 채택하지 않는다. A1을 먼저 해결해야 정확한 원문 연결이 성립한다.

## A6. CI 원문에서 필요한 근거를 선택해 읽기

현재 공통 compact는 로그의 일부 구간·긴 행·일부 상세 문자열을 생략하고 전체 수집 JSON을 evidence_file에 보관한다. 지원되는 컴파일 진단의 원문은 유지하지만, 지원되지 않는 로그의 추가 문맥이 필요하면 에이전트가 JSON 구조를 확인하고 Python 등으로 선택 코드를 작성해야 할 수 있다. 수집이 완전하다는 것과 현재 발췌만으로 원인 분석을 끝낼 수 있다는 것은 다르다.

실제 추가 원문 조회가 필요한 경우에 한해 기존 명령의 읽기 전용 분기로 저장된 자료를 선택해 읽는 기능을 검토한다. 입력은 evidence 파일·예상 SHA·job ID·회차·정확한 구간 또는 명시한 검색 조건이며 출력은 해당 원문·원래 위치·자료 소속·생략 여부다. 원격 전체 수집과 인증을 다시 수행하지 않는다. 최종 CLI 문법은 구현 전에 정한다.

새 API 조회 없이도 같은 원인이 해결되는 경우만 이득 후보로 삼는다. 저장 원문은 그 관찰 시점의 자료이며 최신 CI 상태를 증명하지 않는다. 최초 다운로드가 잘린 자료를 전체 로그로 표현하지 않는다. 직접 처리에도 gh의 필터·정확한 로그 구간 조회와 스크립트를 허용한다. 이미 충분한 진단을 제공하는 실패 사례에는 새 절차를 추가하지 않는다.

| github context | 추가 구현 근거 약함 | 목록 자체가 필요할 때 한 번 조회. 생성마다 선행 실행하지 않는다. |
| github setup | A4 | 기존 설정·정책·권한 보존과 명시적 refresh 구분을 유지한다. |
| github issue create | 현재 연속 작업 유지 | 생성→담당자→Development 연결→워크트리까지 연결돼 있다. partial에서는 기존 이슈를 복구하며 새로 만들지 않는다. |
| github issue branch | 현재 재사용 검증 유지 | 같은 이슈의 연결·워크트리 확인은 실제 안전 조건이다. 반복 검증 시험의 두 호출을 일반 1회 사용으로 해석하지 않는다. |
| github pr create | 이번 추가 구현 근거 약함 | creation_context의 실제 로컬 브랜치 검증을 사용한다. 게시된 head의 PR 생성에 적합하다. |
| github pr submit | A6의 공통 CI 조회 후보만 | 푸시→PR 재사용/생성→검사 대기·결과까지 연결된 흐름을 유지한다. 필요한 sections·wait 선택은 이미 제공한다. |
| github pr reviews | A1·A5 | 원문·diff·전체 페이지·마지막 head 검증을 유지한다. 저장을 의무화하거나 더 많은 캐시를 절감 전제로 만들지 않는다. |
| github pr inspect | A2·A5·A6 | 선택 범위·현재 outstanding·완전성·fresh 원격 확인을 유지한다. changed/unchanged만으로 작업 완료를 판정하지 않는다. |
| github pr delta | 현재 범위 유지 | metadata가 필요한 작업에 사용한다. --include-patch는 API가 제공한 patch이며 전체 텍스트 diff의 완전성 보장이 아니다. 필요하면 직접 Git diff로 완료한다. |
| github pr merge | A6의 공통 CI 조회 후보만 | 검사 대기→실제 머지 확인→해당 브랜치/워크트리 정리를 한 명령으로 유지한다. 수락·queue 진입을 완료로 처리하지 않는다. |
| github ci failures | A6 | run·attempt·SHA·job·진단 근거를 유지한다. CI 실패와 자료 수집 실패를 구분한다. |
| github ci rerun | A6 | 요청 1회·체크포인트·예상 회차 대기·실패 자료까지 유지한다. resume은 새 POST를 보내지 않는다. |
| github dependabot list | 추가 구현 근거 약함 | 서버 필터·전체 페이지·패치 null·영향 버전은 이미 제공한다. |
| github dependabot view | 추가 구현 근거 약함 | 현재 한 번 조회로 끝난다. 작은 필드만 필요한 직접 조회도 허용한다. |
| github branch cleanup | 현재 흐름 유지 | 계획·적용 전 상태 재검증·SHA 조건·작업 중인 워크트리 보호를 유지한다. 삭제 전 검사를 출력 절감을 위해 없애지 않는다. |
| fs inspect | 현재 조회 기능 유지, A1과 연결 | 명시한 raw 원문·공통 섹션/순번·개별 배치·기존 커서를 활용한다. 목차를 먼저 읽거나 도움말 확인을 매번 요구하지 않는다. |
| fs delta | A3 | 최초 기준 생성과 기존 기준 변경 조회를 구분한다. peek·실제 반복 관찰·삭제 전 원문을 유지한다. |
| fs apply | A3 | 정확한 count·preimage·전체 검증·실제 반영·바이트/권한 read-back을 유지한다. preview·계획 저장을 항상 앞에 붙이지 않는다. |
| fs test-results | A3 | 합계·실패/오류/skip 원문·XML 오류·파일 근거를 유지한다. 테스트 프로세스 종료 확인은 별도로 수행한다. |

일반적인 직접 처리로 한 번에 끝나는 작은 검색·치환·단일 필드 조회에는 tools를 강제하지 않는다. 이미 제공하는 조합을 새 명령으로 다시 만들거나 pr merge의 정리를 분리하지 않는다. 다른 작업을 거치지 않는 반복 호출과 모델 입력 캐시 적중을 기본 조건으로 삼지 않는다.

## 구현·검증 순서

1. A1·A2를 먼저 고치고 원문·요청 본문을 한 번에 사용할 수 있는지 기능 검증한다.
2. A3은 JUnit·delta·apply의 읽기/쓰기 상태를 구분해 설계한다. 일반 크기·기본 상한 초과·내용 변경·부분 실패를 나눠 검증한다.
3. A4·A5는 실제 확인을 요청한 작업과 경로를 모르는 리뷰 작업에 한정해 비교한다.
4. A6은 실제 발췌 부족·artifact 가공 사례가 확인될 때 수행한다. 구현만으로 토큰 절감을 주장하지 않는다.
5. 각 변경 작업만 기본 모델·추론 강도로 직접 처리와 tools를 비교한다. 동일 입력·정답·최종 파일·검증 범위, 입력 작성·원문 조회·저장·후처리·재시도·최종 확인을 모두 포함한다.

캐시 포함 총 입력+출력과 캐시 제외 입력+출력, 모델 도구 호출·셸 실행·내부 CLI/API·파일 I/O, 시간·편차·실패를 구분해 기록한다. 설치·발견이 필요한 예제는 이미 설치된 사용과 최초 사용을 구분한다. 독립 1회 사용을 기본으로 하고 다른 작업 후 복귀와 연속 반복은 별도 조건이다. 더 작은 출력 때문에 재조회가 필요하면 그 비용을 포함하며 실패·불리한 실행을 교체하지 않는다.

현재 [최신 측정](benchmarks/usage/README.md)의 리뷰 반영은 총 토큰 +0.6%, 캐시 제외 +31.6%, 시간 +6.4%로 AND 미충족이다. 일반 대화 조회는 토큰·시간이 줄었지만 직접 처리보다 API가 많아 조건부다. 이 기록은 유지한다. 새 후보는 작업 효율과 전체 토큰이 함께 좋아진 경우에만 동시 개선으로 표시하고 캐시 지표가 상충하면 조건부로 기록한다. 빌드 성공과 OS별 실제 동작 검증도 구분한다.

관찰 재현:

```sh
python3 scripts/benchmarks/audit_command_usability.py --output command-usability-audit.json
```

이 실행기는 임시 Go overlay와 기존 fixture를 사용한다. 프로덕션 소스를 수정하거나 실제 GitHub에 쓰지 않으며 모델도 호출하지 않는다. 별도 GOCACHE를 지정할 수 있다. 현재 관찰은 Linux에서 실행했으며 다른 OS의 실제 동작까지 검증한 것은 아니다. [관찰용 코드](../scripts/benchmarks/command_usability_probe.go.txt)의 세 출력 관찰은 결함이 없다는 통과 시험이 아니라 현재 작업 가능성을 보여 주는 자료다.
